# SKTTP/QR 送信・エラーテスト

`index.html`をブラウザで開く。外部ライブラリ・ネット接続・サーバーは不要。
生成済みQRを繰り返し表示する。枚数は16 / 32 / 64 / 128枚で切り替え可能。
全断片が圧縮データ200Bで、全体は3,200 / 6,400 / 12,800 / 25,600B。
速度は200 / 125 / 65 / 50ms。初期値は125ms。ブラウザの描画周期で丸められるため、
端数を次フレームに持ち越して平均速度を保つ。遅いフレームでも断片はスキップしない。

正常モードは正しいSHA-256、GZIP、v1 JSONを持つ授業メモ2件のテストデータ。
受信検証だけならアプリの上書き確認をキャンセルすること。
枚数・送信パターン変更時は共有IDが変わるため、アプリで「新しく読み取る」を選ぶ。
速度の変更は共有IDを変えない。ページの再生成も新しい共有IDになる。

## エラーの送信パターン

- SHA-256不一致: 正常な圧縮データのまま、全断片に同じ誤ったハッシュを設定する。
  全枚数を集めた時点で`DAMAGED`。途中の断片収集は正常に進む。
- 同番号・内容不一致: 正常な#1の直後に、同じID・ハッシュ・番号で200Bのうち
  1ビットだけ変えた#1を挿入する。両方読んだ時点で`DAMAGED`。
  確実に試すなら正常な#1で一時停止して受信させ、「不一致の1枚目を表示」を押す。
  カメラが片方を読み逃した場合、即時エラーが出るとは限らない。
  1周の表示数は論理枚数N+1だが、プロトコルの総枚数はNのまま。

再生成:

```powershell
python tools/qr-loop-test/generate.py
```

Android StudioのJBRとローカルGradleキャッシュのZXing 3.5.4を使用。
生成時に全724枚の画像（4種類の枚数 × 3パターン、改変#1を含む）をZXingで復号し、断片サイズを確認する。
正常データのハッシュ・GZIP・JSONと意図したエラー条件は`verify.cjs`で検証する。
生成された`index.html`だけをコピーして他のPCでも使える。

ページのデータ・再生ロジックの検証（Node.js）:

```powershell
node tools/qr-loop-test/verify.cjs
```

アプリのコンパイル済みCollectorに12ケースを渡す検証（先に`:app:compileDebugKotlin`が必要）:

```powershell
python tools/qr-loop-test/verify_protocol.py
```

正常モードの順不同・重複、SHA-256不一致が最後の断片でのみ起きること、同番号の
改変断片が`DAMAGED`になることを既存Collectorそのものを使って確認する。
